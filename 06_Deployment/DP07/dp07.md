## 📌 체크포인트 답변

### 1 체크포인트
1. **Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리가 어떻게 다릅니까?**
   * **Day 5**: 수치형 데이터를 모델이 학습하기 적합한 범위로 맞추기 위해 표준화/정규화(평균 및 표준편차 기반 스케일링)를 수행합니다.
   * **Day 7**: 자연어 텍스트를 모델이 연산할 수 있는 고유 정수 ID 배열(토큰 텐서)로 변환하는 토크나이징(BPE 알고리즘 등)을 수행합니다.

2. **Hugging Face Transformers 라이브러리의 역할은 무엇입니까?**
   * 사전학습된 다양한 트랜스포머 기반 LLM 및 토크나이저를 손쉽게 다운로드, 로드, 파인튜닝, 텍스트 생성 추론까지 통합 수행할 수 있도록 표준화된 API를 제공하는 라이브러리입니다.

### 2 체크포인트
1. **토크나이저의 encode()와 decode()는 각각 어떤 변환을 수행합니까?**
   * `encode()`: 사람이 읽는 문자열(텍스트)을 모델이 이해하는 숫자 시퀀스(Token ID 텐서)로 변환합니다.
   * `decode()`: 모델이 생성한 숫자 시퀀스(Token ID 텐서)를 다시 사람이 읽을 수 있는 문자열(텍스트)로 복원합니다.

2. **model.generate()의 temperature 파라미터는 생성 결과에 어떤 영향을 줍니까?**
   * 다음 토큰 확률 분포의 무작위성(창의성)을 조절합니다. 값이 높을수록(예: 1.2~1.5) 다양한 어휘와 창의적인 문장이 생성되고, 값이 낮을수록(예: 0.1~0.2) 확률이 가장 높은 일관되고 결정론적인 답변이 생성됩니다.

3. **멀티턴 대화에서 이전 대화 기록을 프롬프트에 포함하는 이유는 무엇입니까?**
   * 트랜스포머 언어 모델 자체는 이전 대화의 기억을 유지하지 못하는 무상태 구조이므로, 대화의 문맥(Context)을 이해하고 이어지는 자연스러운 답변을 생성하도록 프롬프트 맨 앞에 과거 대화 내역을 함께 입력해주어야 합니다.

### 3 체크포인트
1. **ChatRequest의 messages가 리스트인 이유는 무엇입니까?**
   * 단발성 질문이 아닌 시스템 지시, 사용자 질문, 봇 응답 등 시간 순서대로 누적된 멀티턴 대화 기록(`[{"role": "user", "content": "..."}, ...]`)을 순차적으로 전달받기 위함입니다.

2. **서버가 대화 기록을 저장하지 않고, 클라이언트가 매번 전체 기록을 보내는 이유는?**
   * REST 아키텍처의 **무상태(Stateless) 원칙**을 따르기 위함입니다. 서버가 세션 상태를 저장하지 않으면 서버 확장(Scale-out)이 자유로워지고, 서버 장애 시에도 세션 유실 없이 부하 분산 처리가 쉬워집니다.

3. **max_new_tokens을 너무 크게 설정하면 어떤 문제가 발생할 수 있습니까?**
   * 생성 시간이 비례해서 늘어나 서버 응답 지연(Latency)이 심해지고, GPU/CPU 연산 자원이 낭비되며 모델의 최대 처리 토큰 한도(`max_position_embeddings`)를 초과할 위험이 발생합니다.

### 4 체크포인트
1. **st.chat_message와 st.chat_input은 각각 어떤 역할을 합니까?**
   * `st.chat_message`: 지정한 역할(`user`, `assistant` 등)의 아바타 아이콘과 함께 말풍선 스타일로 메시지를 화면에 렌더링합니다.
   * `st.chat_input`: 화면 하단에 고정된 ChatGPT 형태의 텍스트 입력창을 띄우고, 엔터 키 입력 시 사용자 입력을 받아옵니다.

2. **st.session_state["chat_messages"]에 대화 기록을 저장하는 이유는?**
   * Streamlit은 사용자의 인터랙션이 발생할 때마다 전체 스크립트를 처음부터 다시 실행(Rerun)하므로, 새로고침되어도 이전 대화 내역이 화면에서 사라지지 않고 유지되도록 브라우저 세션 상태에 저장합니다.

3. **"대화 초기화" 버튼이 st.rerun()을 호출하는 이유는 무엇입니까?**
   * `st.session_state`의 대화 리스트를 비운 직후 화면을 즉시 다시 렌더링하여 초기화된 빈 대화창 상태를 UI에 바로 반영하기 위함입니다.

### 5 체크포인트
1. **챗봇 API에서 인증이 실패하면 서버는 어떤 상태 코드를 반환합니까?**
   * `HTTP 401 Unauthorized` 상태 코드를 반환합니다.

2. **UI의 call_chat_api()는 401 응답을 받으면 사용자에게 무엇을 보여줍니까?**
   * `"🔑 인증 실패. API Key를 확인하세요."`라는 경고 에러 메시지(st.error)를 출력합니다.

3. **Day 6의 인증 모듈(app/auth.py)을 Day 7에서 수정 없이 재사용할 수 있는 이유는 무엇입니까?**
   * FastAPI의 의존성 주입(`Depends(verify_api_key)`) 구조는 HTTP 요청 헤더(`X-API-Key`)만을 독립적으로 검사하므로, 바디에 담기는 데이터 형식(이미지 파일인지 JSON 텍스트인지)과 완전히 분리되어 재사용이 가능합니다.

## 🏆 Day 7 최종 체크포인트

* **Q1. Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리 방식의 차이는?**
  * Day 5는 테이블 형태의 수치 데이터를 모델 수렴을 돕기 위해 평균/표준편차로 스케일링(정규화)하였고, Day 7은 비정형 자연어 문자열을 토크나이저(BPE)를 통해 정수 토큰 ID 시퀀스로 인코딩하는 전처리를 거칩니다.

* **Q2. 멀티턴 대화에서 서버가 상태를 유지하지 않는 이유는?**
  * 무상태(Stateless) 설계를 유지하여 서버의 확장성과 신뢰성을 확보하기 위함입니다. 서버가 세션을 메모리나 DB에 직접 물고 있지 않으므로 다중 인스턴스 환경에서도 로드 밸런싱이 자유롭고 서버 부담이 최소화됩니다.

* **Q3. API Key가 잘못되면 서버는 어떤 상태 코드를 반환하고, UI는 어떻게 처리합니까?**
  * 서버는 `HTTP 401 Unauthorized`를 반환하며, UI는 `requests.exceptions.HTTPError` 예외를 감지하여 사용자에게 API Key 확인을 요청하는 직관적인 경고창(`🔑 인증 실패`)을 표시합니다.

* **Q4. temperature를 낮추면 생성 결과에 어떤 변화가 있습니까?**
  * 토큰 확률 분포가 첨예화되어 가장 확률이 높은 단어 위주로 선택되므로, 답변이 일관되고 문법적으로 안정적이며 예측 가능(결정론적)해집니다.

* **Q5. 이 서비스를 다른 컴퓨터에서 실행하려면 무엇이 필요합니까?**
  * Python 실행 환경과 필수 라이브러리(`transformers`, `torch`, `fastapi`, `uvicorn`, `streamlit`, `pydantic`, `accelerate`) 의존성이 설치되어 있어야 하며, Hugging Face 모델 가중치 파일 다운로드 및 서버 구동 스크립트 실행 환경이 필요합니다.
